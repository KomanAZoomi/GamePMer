## 0. 本文定位

**这是执行清单，不是对齐文档。** 对齐已经完成：业务对齐以设计说明为准，视觉对齐以 `docs/design-assets/` 的原型图为准。
本文只回答一个问题：**按什么顺序做、每一步停在哪里给用户看。**

M1 的失败不是代码失败，是「一次做完六大块才交付」。因此本文的核心不是任务分解，而是**检查点与截图门**。
任何一个检查点没有经过用户看真实页面，后续检查点不允许开工——即使用户说过「继续直到完成」。

本轮范围：设计说明 §13 的切片 1、2、4 重组成的**第一个可验收纵向闭环**。切片 3（候选收件箱）、5（报价变更）、
6（结项出账）、7（连接器与运维）不在本轮，理由见 §8。

## 1. 五分钟演示脚本（S0 需求钉子）

这是本轮的验收基准。从 C2 起，每个检查点结束时这份脚本必须可运行（允许后半段尚未实现，但已实现部分必须能连续走完）。

**场景：周一早上，PM 打开工作台，处理客户对机甲主角高模的反馈。**

| 步 | 操作 | 必须看到什么 |
|---|---|---|
| 1 | 打开工作台首页 | 不是空白页。三个项目、四个指标卡有真实数字、任务看板有分组、右侧有一条待处理的客户反馈 `F-017` |
| 2 | 点击「P-3D-024 高模肩甲比例返修」 | 右侧智能详情显示反馈来源、影响资产 `MECH-01`、影响节点数、AI 建议（未执行） |
| 3 | 跳转到项目甘特 | 看到 `MECH-01` 六个 PBR 阶段各自独立的日期条，不是一根项目进度条；周末有底纹；今天线在 7/27；中模已验收、高模标客户反馈 |
| 4 | 切到排期管理，看 3D-A 组本周档期 | 该组已排人天 / 可用人天，以及一条可解释的超载来源（点得进去，能看到是哪个项目哪个阶段占的） |
| 5 | 回到反馈中心，把 `F-017` 第一项判为范围内返修，填 2 个工作日 | 甘特上出现**草案层**：高模及其后续未验收阶段整体右移，基准条和当前条同时可见，未受影响的 `MECH-02` 和其他项目不动 |
| 6 | 手工把低模草案再右移 1 个工作日 | 新旧日期对比、工作日增量、受影响节点数实时更新；落到周末的日期自动跳到下一个工作日 |
| 7 | 点「取消草案」 | 正式计划**完全没变**，甘特回到第 3 步的状态 |
| 8 | 重新生成草案 → 填写原因「客户反馈」→ 确认 | 当前计划更新、基准条保持原位、生成修订 v2、生成两封**未发送**通知草稿（组长 + 艺术总监） |
| 9 | 刷新浏览器 | 修订仍在，可查看 v1→v2 历史 |
| 10 | 点「恢复示例数据」 | 回到第 1 步的初始状态 |

**这份脚本走不通，本轮就没有完成，与测试是否全绿无关。**

## 2. 检查点

每个检查点的完成定义统一为：

1. 先写失败测试（领域规则）或组件交互测试（页面行为）。
2. 实现到测试通过。
3. `npm.cmd test` / `npm.cmd run lint` / `npm.cmd run build` 三项全过。
4. 在 1280 / 1440 / 1920 三档截图。
5. **把截图和本地地址交给用户，等用户回话。**
6. 用户确认后才进入下一个检查点。

### C0 — 工程地基（无用户验收）

唯一一个不设截图门的检查点，因为没有可看的东西。控制在最小范围。

- 创建工作树：`git worktree add .worktrees/intranet-web-redesign -b feat/intranet-web-redesign feat/web-schedule-replan-demo`，然后 `git merge main` 取回文档与设计资产。
- 建立设计令牌 `src/styles/tokens.css`：白 / 浅暖灰层级、鼠尾草绿、琥珀、克制红、间距、圆角、阴影、字号阶梯（**正文最小 14px**）。
- 建立固定时钟 `src/domain/clock.ts`：Demo 时钟固定为 `2026-07-27`，通过依赖注入传入用例层。理由见 §5。
- 删除旧 `App.tsx` / `App.css` 的视觉实现，保留 `domain/` 与 `data/` 暂不动。
- 补 `@playwright/test` 依赖但**不写用例**，同时把 `test:e2e` 脚本改成明确的占位说明，消除「脚本存在但跑不起来」的假象。

### C1 — 白色外壳与首页（第一个截图门）

**对照：** `screenshots/01-white-home.png` + `prototypes/white-reference-clone-home-v1.html`

**可见验收场景：** 打开 `/`，看到完整工作台，不是空白页。

- 左侧完整 10 项导航，全部展开、不折叠；顶部全局搜索、消息/邮件计数、新建任务。
- 四个指标卡（今日待办 / 进行中 / 已完成 / 逾期）数字**由种子数据算出**，不是写死的字符串。
- 左列任务看板按「需求评审 / 产品制作 / 结项与备份」分组；中央阶段卡阵列；右侧智能详情面板。
- 底部跨项目时间线。
- 路由骨架：10 个导航项全部可点，未实现页显示明确的「本切片未实现」占位，**不允许点了没反应**。
- 「恢复示例数据」入口。

**先写的测试：** 指标卡数字来自 state 的计算函数；导航 10 项齐全；任务项能追溯到项目/资产/来源。

**用户验收问题：** 信息密度对不对？术语对不对？字号会不会小？这一屏是不是你每天想第一眼看的东西？

### C2 — 项目详情与真实甘特（最高风险检查点）

**对照：** `screenshots/04-project-gantt.png` + `screenshots/04-reference-gantt-comparison*.jpg`

这是 M1 直接翻车的地方（失败点 4、5），单独成门，不与其他内容混合交付。

**可见验收场景：** 演示脚本第 3 步。

- 日历头：15 天窗口（`2026-07-27` ~ `2026-08-10`），周末底纹、今天线、月/周/日轴切换、横向滚动。
- 左侧行表：资产分组行 + 阶段行，含负责人、状态胶囊、进度（如 `6/8`）。
- 三层 bar 并存：基准（灰）/ 当前（绿）/ 实际（深色细条），客户等待与反馈区间用琥珀色区间条。
- 状态不只有颜色：每个状态同时有文字标签。
- 右侧阶段详情抽屉：基准 / 当前 / 实际 / 提交客户 / 客户确认五组日期，前置依赖，AI 建议。
- 底部修订版本时间线（此时只有 v1）。

**先写的测试：** 日期 → 百分比定位的纯函数；工作日与周末判定；基准条不随当前条变化；实际日期缺失时不渲染实际条。

**用户验收问题：** 这张甘特图能不能替代你现在看排期的方式？缺哪一列？

### C3 — 排期管理与团队档期（先补原型，再实现）

**这是七个核心页面里唯一没有原型的一个**，且直接对应 M1 失败点 3「录入排期和档期太过简单」。

因此本检查点**拆成两步**，中间插一次用户确认：

- **C3a：** 先产出静态 HTML 原型（跨项目组合排期 + 制作组周容量 + 节点清单 + 计划录入抽屉），交用户确认。
  产物存入 `docs/design-assets/2026-07-27-white-ui/prototypes/schedule-capacity-page-v1.html` 并截图。
- **C3b：** 用户确认后再实现。

**C3b 可见验收场景：** 演示脚本第 4 步。

- 组合排期：三个项目的全部阶段节点在一个视图内可见。
- 制作组周容量：可用人天 / 已排人天 / 预留 / 超载差额，超载能下钻到具体项目与阶段。
- 计划录入抽屉：每个资产展开到可验收阶段，含制作组、预估人天、起止日、依赖、验收节点；**不允许退化成两个日期文本框**。
- 冲突检查：非工作日、依赖倒置、人天与日期区间不匹配、同组超载。

**先写的测试：** 容量占用聚合（跨项目共享制作组，不挂成项目私有）；四类冲突检查各一条；客户等待不消耗人天但占时间线。

### C4 — 反馈中心与草案生成

**对照：** `screenshots/05-feedback-center.png`

**可见验收场景：** 演示脚本第 5、6、7 步。

- 反馈批次列表 → 资产级反馈项拆分；每项可判定范围内返修 / 范围外新增。
- 右侧原始证据、反馈盘路径、AI 分类建议（标注依据，可拒绝）、影响分析。
- 范围内返修 → 生成排期草案：甘特上出现第四层草案 bar（斜纹 + 虚线描边），与正式计划视觉可区分。
- 草案可按整工作日手工调整，落在休息日时自动顺延到下一工作日。
- 底部草案预览：旧日期 / 新日期 / 工作日增量 / 受影响节点 / 未受影响资产。
- **取消草案后正式计划零变化**（这条要有专门的测试，不只是手测）。
- 范围外新增只创建变更单占位并跳转提示，不在本轮实现报价流程。

**先写的测试：** 草案生成不写 `StagePlan.current*`；只顺延未验收阶段；跨资产不误伤；客户等待归因与团队延期分开计算。

### C5 — 确认事务、修订与通知草稿

**可见验收场景：** 演示脚本第 8、9 步。

- 确认对话：必填原因（客户反馈 / 团队延期 / 范围变更等），备注可选。
- 原子事务：一次性写入修订版本 + 更新受影响阶段 + 生成审计事件 + 生成通知草稿；任一失败全部回滚。
- 基准日期保持不变，可与当前日期并排比对。
- 通知是 `unsent` 草稿，需 PM 主动发送；本轮「发送」只记录发送证据，不真发。
- 刷新后修订仍在，可查看 v1 → v2 历史。

**先写的测试：** 事务回滚（注入一个中途失败的 Repository，断言 state 未被部分修改）；确认时间来自注入时钟而非反馈接收日；审计事件含操作人/时间/原值/新值/来源。

### C6 — 闭环整合与三档视觉回归

## 3. 第一闭环的领域模型裁剪

设计说明 §7 列了 24 个对象。**本轮只实现闭环真正需要的 11 个**，其余留类型定义占位或完全不建。
先建全部 24 个对象等于「先建所有表再做 UI」，正是 CLAUDE.md §14 明令禁止的顺序。

| 本轮实现 | 本轮不实现（留占位或不建） |
|---|---|
| `Project` `Asset` `StagePlan` | `InboxCandidate` `SourceRecord`（C4 用固定证据对象代替） |
| `ProductionGroup` `CapacityBucket` | `QuoteCase` `QuoteVersion` `QuoteLine` |
| `FeedbackBatch` `FeedbackItem` | `ChangeRequest`（只建占位，供范围外反馈跳转） |
| `ScheduleRevisionDraft` `ScheduleRevision` | `CloseoutCase` `CloseoutGate` |
| `WorkCalendar` `NotificationDraft` `AuditEvent` | `Person` `ProjectRole`（本轮用字符串负责人） |

现有 `domain/model.ts` 的改造要点：

- `Stage` → `StagePlan`：补 `productionGroupId`、`estimatedPersonDays`、`actualStart/actualFinish`、
  `submittedToClientAt`、`clientApprovedAt`、`dependsOn`、`revisionReason`。
- 当前的 `StageStatus` 四值不够，拆成**主状态**（`NotStarted → InProduction → HandedToPm → SubmittedToClient → AwaitingClient → Approved`）
  与**可叠加标记**（`Rework` / `WaitingChangeQuote` / `PossibleDelay` / `ScheduleRevisionRequired`）两个字段。
  合并成一个枚举是 CLAUDE.md §16 点名的失败模式。
- `FeedbackBatch` 拆成批次 + 资产级 `FeedbackItem`，现有的「一个批次一个资产」模型不够。
- `WorkCalendar` 从「只判周末」扩展到公司休息日与特殊工作日覆盖。

**可复用的存量代码**（诚实评估：有效逻辑约 100 行，工程基线的价值大于代码本身）：
`moveByWorkdays` / `countWorkdays` 的算法、`replan.ts` 的「草案不污染正式排期」结构、Repository 边界模式、
Vitest + Testing Library 的测试布局。`App.tsx` 全部重写。

## 4. 甘特图技术方案

**结论：自研，零新增依赖。**

依据是原型 `project-detail-gantt-page-v1.html` 已经验证了实现路径：日历头 `grid-template-columns: repeat(N, 1fr)` 等分，
bar 用 `position: absolute` + 百分比左偏移与宽度，四层 bar 靠 `top` 错位叠放（基准 / 当前 / 实际 / 草案），
今天线是一条绝对定位竖线，周末底纹用重复渐变。

不用现成甘特库的理由：需求是**同一行叠四层日期 + 客户等待区间 + 依赖 + 容量占用**，
主流库都围绕「一行一条 bar + 依赖箭头」建模，四层叠加要和库对抗；且内网部署环境下少一个依赖就少一份审查成本。

实现约束：

- 日期 → 百分比是纯函数，单独测试，不写在组件里。
- **不照抄原型的 px 数值。** 原型为了在演示页里缩放展示用了 6~10px 字号，实际实现正文不小于 14px，
  行高与列宽相应放大。原型定的是结构和层次，不是尺寸。
- 时间轴窗口可切换（月/周/日），但第一版先保证日视图正确。

## 5. 种子数据与案例数据

用户已确认：**制作过程中可以自由创建案例数据用于验证。** 据此定三条规则：

1. **种子数据是一等公民，与页面同步交付。** 每个检查点开工前先把该检查点需要的种子数据补齐，
   不允许出现「页面做完了但没数据可看」的中间态。
2. **固定时钟。** Demo 时钟锁定 `2026-07-27`，甘特窗口 `2026-07-27 ~ 2026-08-10`（与原型一致）。
   不锁的话种子数据会随真实日期漂移，截图无法复现，验收无法重来。真实时钟留给正式环境注入。
3. **一键恢复。** 每次验收都从相同初始状态开始。

必须覆盖的状态（设计说明 §11）：正常阶段、T-1 提醒、可能延期、客户等待、客户反馈、范围内返修、
追加报价占位、未确认草案、制作组容量预警、来源与路径证据。

主路径锚点：`P-3D-024 / MECH-01 / F-017`，对照项目 `P-2D-018`（2D 三阶段、等待客户）与 `P-3D-031`（多资产正常制作）。
全部虚构脱敏。

## 7. 质量门禁

每个检查点必过：

```powershell
npm.cmd test
npm.cmd run lint
npm.cmd run build
```

`npm.cmd run test:e2e` 在 C6 补齐 Playwright 依赖、配置和真实用例后才允许声称可用。

**自动测试不能替代视觉验收。** 每个检查点必须同时给出：可访问的本地地址 + 三档截图 + 一句「请你亲手走这一步」。

## 8. 本轮明确不做

- 候选收件箱、报价与变更、结项出账的完整实现（页面留占位与跳转）。
- 任何后端、数据库、账号、权限、审计存储。
- 连接器（邮件 / 企微 / 飞书）与真实 LLM 调用；AI 建议在本轮是种子数据里的固定文案，标注为「示例建议」。
- 加密、备份、打包、部署。
- 移动端适配。

理由是复盘硬规则第 7 条：**基建排在体验之后。** M1 把精力花在 SQLCipher 和 DPAPI 上，
而用户每天要摸的甘特图是最后拼进去的简化版。本轮反过来。

## 9.1 实施期已确认决策

实施过程中遇到、经用户当面确认的取舍。它们**覆盖**设计说明的字面表述，后续检查点按这里执行。

### D1 — 项目详情页不放常驻项目列表（2026-07-27 确认，C2）

项目切换改为页头的项目卡片行。

**为什么：** 左侧项目列表（244px）+ 右侧阶段详情（312px）在 1440 下只给日历留下约 340px，
时间轴读不出任何节点——那等于没有甘特。已确认原型 `project-detail-gantt-page-v1.html` 也没有项目列表。

**代价：** 这一页看不到客户名、负责人等项目组合维度的信息。设计说明 §6.8 的「项目总览」
（按客户/类型/负责人/健康度查看组合）尚未实现，后续需要单独的组合视图或抽屉式详情来补。

**适用范围：** 所有「左列表 + 主工作区 + 右详情」的三栏页面都要先算横向预算，
主工作区需要时间轴的（排期管理、反馈重排）优先保证主区宽度。

### D2 — 「可能延期」使用克制红（2026-07-27 确认，C2）

**与设计说明 §4.3 的差异：** 该条写「克制红只用于已确认的高风险、阻断和逾期」，
严格按字面「可能延期」尚未确认，应当用琥珀。

**为什么按红色执行：** 全图仅此一处红色，它恰恰是 PM 当天最该处理的阻断点；
琥珀已同时承担客户反馈、等待客户和待确认草案，再叠一层会失去区分度。

**约束：** 红色仍然只给「可能延期」和「已逾期」两种状态，不得扩散为普通强调色；
且状态必须同时有文字标签，颜色不是唯一编码。
