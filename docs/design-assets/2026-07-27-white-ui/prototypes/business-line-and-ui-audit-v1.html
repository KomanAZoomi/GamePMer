从需求到出账：业务线与 UI 架构检查

首页结构可以保留，但它应当是“每日总控台”；正式业务状态必须沉淀在项目、资产、阶段、反馈、变更和结项记录中。

检查结论 视觉框架已经成立，核心风险不在“好不好看”，而在首页目前把任务当成主对象。游戏美术 PM 的真实主线应以项目为根，任务只是从项目状态投影出来的个人行动项。
可继续，但需先校正数据主线 保留左侧导航、中央阶段牌、右侧智能详情和底部时间线；调整它们各自承担的业务职责。

以 3D PBR 项目为例，覆盖报价、制作、反馈重排、结项与出账。

报价与排期

验收与结项

全部资产验收后，请总监整理最终包，通知 IT 剪切与备份。

07

出账与归档

汇总原报价、追加报价、交付清单和客户确认，通知 BD 出账。

文件与归档
形成可追溯的项目证据链
客户反馈必须分流这是整条业务线最容易被做错的地方，两条路径不能共用一个“处理反馈”按钮直接重排。
A. 合同范围内返修反馈任务 → 计算受影响节点 → 生成工作日重排草案 → PM 确认 → 更新当前排期。
B. 新增需求 / 超范围修改冻结受影响资产 → 创建变更单 → 追加报价与排期 → 复核通过 → 再进入制作。

各版块如何围绕同一条数据主线

不要让任务、反馈、排期和邮件各自保存一套互不相干的数据。

项目 Project› 资产 Asset› 阶段 Stage› 行动项 Work Item› 证据 Evidence
任务管理只显示“我现在该处理什么”，不是数据源。
项目总览项目健康度、负责人、客户、资产和当前阶段。
候选收件箱未确认的邮件、消息、截图和文件路径。
排期管理基线 / 当前 / 实际日期、依赖、工作日和资源。
反馈中心反馈批次、来源、资产任务、责任原因和返修状态。
报价与变更首次报价与追加报价共用审批证据，不混入普通返修。
结项中心最终包、客户确认、IT 回执、BD 出账的串行门槛。
文件与归档提交盘、反馈盘、最终包和原始消息的统一索引。

当前首页的主要问题

这些问题若不先处理，页面越丰富，后续信息越容易失真。

高
任务被误当成业务根对象应改为项目驱动；首页任务只是跨项目的行动视图。
高
中央阶段牌不能替代甘特图它只展示当前阶段；完整依赖、节点、基线与实际值必须在排期详情页。
高
AI 建议与正式动作界线不够需要明确“建议 / 草案 / 已确认”，并展示原始邮件或反馈证据。
中
首页指标过于通用改为今日必办、节点前 1 天、等待客户、可能延期、待报价、结项阻塞。
中
缺少责任原因与来源追溯需要区分团队延期、客户反馈滞后、需求变更，并保留原始消息链接。
首页定位每日总控台：只呈现今天要判断和处理的事项。
项目定位唯一业务主线：资产、阶段、反馈、排期、报价全部挂靠项目。
AI 定位负责识别、归类、生成草案；任何正式更新都由 PM 确认。
排期定位首页轻量预览，项目详情提供真正可编辑、可回溯的甘特图。
导航定位保留完整模块数量和持续展开状态，不折叠、不删减入口。
确认：采用“项目为根、首页为总控、反馈双分流”的业务架构

确认后继续拆解：候选收件箱 → 项目详情与甘特图 → 反馈重排 → 报价变更 → 结项出账。
