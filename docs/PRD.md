## 2. 背景

目标用户每天需要处理四类相互关联的工作：

1. 监控 2D/3D 美术资产的阶段排期、客户确认和延期风险。
2. 从企业微信、飞书和邮件收集客户反馈，整理到反馈盘并通知内部负责人。
3. 从团队完成邮件中获取资产路径，随后向客户正式提交并跟踪确认。
4. 承接 BD 报价需求，组织总监报价和组长复核；项目完成后推动最终包、IT 备份和 BD 出账通知。

当前信息分散在聊天、邮件、Excel 和文件盘中。并行项目超过 15 个、每日待判断信息超过 100 条，PM 需要依赖记忆维持项目全貌，难以及时分辨风险来源和后续影响。

## 3. 问题定义

### 3.1 显性痛点

- 信息无法第一时间同步到统一位置。
- 排期压力大，节点变化需要频繁手工调整。
- 每天反复收集、转发、归档和查找信息，工作疲劳明显。

### 3.2 潜在痛点

- 同一条信息在多个渠道重复出现，造成重复处理。
- “制作完成”“内部审核完成”“已提交客户”“客户确认完成”缺少明确区分。
- 连续群消息中的反馈容易被拆散、漏记或关联到错误版本。
- 客户反馈延迟、客户反复修改和团队延期经常混为同一类排期偏差。
- 原报价与追加需求缺少统一版本链路，结项时需要重新翻找依据。
- 等待他人回复的事项缺少清晰的等待状态、截止时间和升级提醒。
- 项目结项依赖总监、IT 和 BD，但缺少统一结项门和完成证据。
- PM 实际承担人工消息总线角色，一旦未及时转发，流程就会停顿。

## 4. 产品愿景

GamePMer 是游戏美术 PM 的“项目控制塔”：把外部信息转换成可确认的候选事项，将确认后的结果关联到项目、资产、阶段、反馈、报价和结项流程，并以异常优先的方式呈现项目真实状态。

产品不代替 PM 做业务决策。它减少记忆负担、提供一致的状态定义和证据链，让 PM 将精力用于判断优先级与协调资源。

## 5. 产品目标与成功标准

### 5.1 核心目标

1. 打开首页后 10 秒内识别今天必须处理的高风险事项。
2. 对任意项目，可以追溯最新排期、原始消息、反馈批次、提交版本和责任状态。
3. 清晰区分团队延期、客户等待、返修、需求变更和连接异常。
4. 重要节点、T-1 提醒和阻塞事项基本不遗漏。
5. 工作台成为正式排期的唯一数据源，Excel 仅用于迁移、导出和备份。

### 5.2 首版验收指标

| 指标 | 验收方式 |
| --- | --- |
| 重要事项遗漏 | 连续 20 个工作日试用中，由用户标记的 P0 事项遗漏数为 0 |
| 风险发现时间 | 用户在首页 10 秒内能指出当天全部延期、T-1 和待重排事项 |
| 状态可追溯 | 抽查 20 个状态变更，100% 能定位到人工操作或原始信息 |
| 排期归因 | 抽查全部延期记录，100% 具备团队、客户、变更或其他原因 |
| 数据可靠性 | 强制退出后重启，已确认数据无丢失；最近一次本地备份可恢复 |

时间节省属于观测指标，不作为唯一成败标准。用户明确优先要求项目状态与排期风险随时清楚。

## 6. 用户与职责边界

### 6.1 主要用户

- 游戏美术 PM，单用户使用。
- 每位试用同事安装独立副本，使用独立数据库和密钥，数据互不共享。

### 6.2 外部角色

- BD：提供报价需求；接收最终报价和出账通知。
- 2D/3D 总监：返回报价与排期，整理最终提交包。
- 组长：复核报价；同一个人可能同时担任 BD。
- 制作团队：完成内部制作和审核后，通过邮件交付文件路径。
- 客户：在项目群或邮件中确认阶段结果、提供反馈和追加需求。
- IT：执行最终资产剪切备份，并邮件回复完成情况。

### 6.3 不纳入产品职责

- 不管理组内审核流程。
- 不管理具体制作人员或个人绩效。
- 不自动发送邮件、群消息或客户催办。
- 不自动修改后续排期。
- 不直接移动最终资产或执行 IT 备份。
- 通知 BD 出账后，不继续跟踪开票或回款。

### 7.1 P0：M1 基础与排期控制塔

> 本节的功能清单仍然成立，但承载形态已改为内网 Web。
> 「本地数据库、本地自动备份、加密迁移包、MSIX」等条目属于已废弃的桌面方案。

- ~~Windows 单用户本地应用~~ → 公司内网 Web 工作台。
- 项目、资产、2D/3D 阶段模板。
- 资产阶段级人天、计划开始日和计划完成日。
- 基准排期、当前排期和实际日期分离。
- 工作日日历、公司节假日和 T-1 计算。
- 手工重排、排期修订记录和偏差原因。
- 混合控制台、完整阶段表和甘特时间线。
- 高风险即时提醒、普通信息可配置时间汇总。
- Excel 历史排期导入和当前排期导出。
- 本地数据库、本地自动备份、恢复和加密迁移包。

### 7.2 P0：M2 Outlook 与 AI 候选收件箱

- 经典 Outlook 指定文件夹只读接入。
- 邮件线程、附件和文件路径识别。
- 完成邮件、BD 需求、报价回复、复核、IT 确认分类。
- AI 候选项目、资产、阶段、日期、路径、类型与摘要。
- 人工确认、驳回、修改、重复合并和原文追溯。
- Outlook 草稿创建；不自动发送。
- LLM 供应商预设、API Key 本地加密和测试连接。

### 7.3 P1：M3 反馈中心与项目群

- 飞书和企微官方能力验证。
- 固定项目群与项目自动绑定。
- 混合项目群通过项目编号、资产编号和上下文路由。
- 同项目、同资产、同群、限定时间窗内的连续消息自动合并。
- 反馈批次主卡片和资产反馈子任务。
- 文件命名解析：`资产名_阶段名_YYYYMMDD_rNN`。
- 反馈盘目录模板、原始消息、截图、附件和摘要归档。
- 无接口权限时提供转发机器人、快捷粘贴和截图导入。

### 7.4 P1：M4 报价、变更与结项

- BD 半结构化需求提取。
- 2D/3D 固定总监自动建议；混合需求拆成子报价。
- 固定报价表导入和自由邮件报价提取。
- 报价版本、组长/BD 复核依据和人工通过门。
- 开工依据记录和开工邮件草稿。
- 追加需求、追加报价、局部冻结和排期更新。
- 客户最终确认、最终包、IT 备份和 BD 出账闭环。
- 固定结算模板自动汇总。

### 7.5 P2：M5 分析与发布

- 制作组并行项目、资产和阶段节点密度。
- 预计人天与实际偏差。
- 客户等待、返修和追加需求影响分析。
- MSIX 安装包、内网分发和受控更新。
- GitHub CI、脱敏样例和发布检查。

## 8. 信息架构

主导航包含：

1. 今日控制台。
2. 统一收件箱。
3. 项目与排期。
4. 反馈中心。
5. 报价与变更。
6. 结项中心。
7. 归档与搜索。
8. 模板与设置。

项目是业务信息的根对象。消息、附件、反馈、报价、排期修订和结项证据都必须关联项目；无法识别项目的信息只能停留在候选收件箱。

## 9. 详细功能需求

### FR-001 今日控制台

控制台默认采用“异常优先的混合布局”，顶部显示今日需处理和排期风险，中部显示项目/资产阶段条，底部显示高优先级事项。

即时风险类型：

- 已延期或今天到期。
- T-1 提醒草稿尚未处理。
- 报价截止临近。
- 无法归类的高优先级客户反馈。
- 连接器异常或数据长时间未同步。
- 结项流程关键步骤阻塞。

普通信息按用户配置的固定时间汇总；系统提供上班、午后、下班前的默认时间模板。

**验收条件：**

- 可以按项目、制作类型、阶段、风险原因和日期过滤。
- 默认只显示异常与当天必须处理项。
- 点击风险可以定位到项目、资产、阶段和证据来源。
- 风险处理完成后从当前视图消失，但审计记录保留。

### FR-002 项目与资产

项目至少包含：项目编号、名称、客户、2D/3D 类型、BD、组长、艺术总监、项目群、制作盘、提交盘、反馈盘、工作日日历和客户反馈时限。

资产至少包含：资产编号、名称、制作类型、阶段模板、当前阶段、预估人天和状态。

系统内不记录具体制作人员。负载仅分析到制作组、项目、资产和阶段层级。

**验收条件：**

- 项目编号唯一。
- 同一人员可以同时承担 BD 和组长角色，通知时自动去重。
- 2D/3D 阶段模板可复制到项目并允许项目级调整。
- 删除已产生业务记录的项目必须改为归档，不允许物理删除。

### FR-003 阶段排期

默认阶段：

- 2D：草图、细化 50%、完成稿。
- 3D：中模、高模、低模、烘焙、贴图、LOD。

每个阶段保存：预估人天、基准开始/结束、当前开始/结束、实际开始/完成、提交时间、客户确认时间和偏差原因。

每个阶段必须等待客户确认后才能进入下一阶段。组内审核不在系统内管理；团队完成邮件代表资产已经完成内部流程并交接给 PM。

**验收条件：**

- 基准日期在项目正式开工后不可覆盖。
- 当前日期只能由 PM 明确保存后更新。
- 当前阶段延期时，后续阶段标记“排期待确认”，但日期不自动变化。
- 每次调整记录修改前后日期、原因、时间和操作人。
- 周末和公司节假日默认不计入人天；特殊加班日可以单独启用。

### FR-004 T-1 与完成邮件

如果阶段计划完成日前一个有效工作日仍未收到团队完成邮件，系统生成提醒卡片与邮件草稿。只有 PM 确认后才写入 Outlook 草稿箱。

团队完成邮件需要提取项目、资产、阶段、文件路径和发件人，生成“待提交客户”候选卡片。

**验收条件：**

- T-1 使用工作日日历计算。
- 已收到并确认对应完成邮件时，不再生成提醒。
- 同一阶段只保留一个活动提醒，避免重复草稿。
- 提醒被忽略、延期或完成后均保留操作记录。

### FR-005 客户提交与反馈等待

PM 从团队邮件路径取件后，通过客户指定渠道提交，并手工确认“已提交客户”。系统记录客户反馈截止日。

客户反馈逾期时：

- 状态变为“客户反馈逾期”。
- 生成项目群催办文案，但不自动发送。
- 标记可能受影响的后续节点。
- 不立即修改后续排期。

客户反馈实际回来后，PM 根据真实延迟天数手工重排，原因记录为“客户反馈延迟”。

### FR-006 统一候选收件箱

所有连接器产出的原始信息先写入不可变来源记录，再生成候选卡片。候选状态包括：新建、待确认、已确认、已忽略、重复。

候选类型至少包括：

- 客户反馈。
- 团队完成通知。
- BD 报价需求。
- 总监报价回复。
- 组长/BD 复核意见。
- 开工依据。
- 最终包路径。
- IT 备份完成。
- 其他需人工判断的信息。

**验收条件：**

- AI 结果必须显示置信度和原始依据。
- 无法识别项目或资产时，不得直接创建正式记录。
- 用户确认前，不改变项目、资产、阶段或排期。
- 重复项保留指向主记录的关系，原始信息不丢失。

### FR-007 项目群消息路由

支持两种群聊模式：

- 固定项目群：群与项目绑定，默认归入该项目。
- 混合项目群：通过项目编号、资产编号、附件文件名和近期上下文识别。

同项目、同资产、同群且消息间隔不超过配置时间窗的连续消息自动合并。默认时间窗为 15 分钟；出现新的项目编号、资产编号或明确话题切换时停止合并。

### FR-008 反馈批次

反馈采用两层模型：

- 反馈批次主卡片：客户、项目、提交版本、时间、来源群和整体说明。
- 资产反馈子任务：资产、阶段、反馈内容、附件、状态和完成日期。

所有子任务完成后，主卡片才可进入“待重新提交”。项目固定配置组长与艺术总监，系统自动带出建议收件人，但 PM 必须确认。

### FR-009 版本与反馈盘

提交版本默认命名：`资产名_阶段名_YYYYMMDD_rNN`。

反馈盘使用项目级目录模板。用户确认“一键归档”后才执行文件写入，归档内容包括原始消息、时间、截图、附件、反馈摘要、资产清单和来源定位信息。

### FR-010 报价需求

BD 报价邮件为半结构化输入。系统提取客户、项目、类型、资产清单、数量、规格、参考资料、期望交付时间、报价截止时间和信息缺口。

2D/3D 各有固定总监；混合需求拆成两个子报价任务。全部子报价返回后，生成合并预览。

总监报价可能来自固定表格或自由邮件。系统保留每个报价版本及原始附件，不覆盖旧版本。

### FR-011 报价复核与开工

组长复核结论可能来自邮件、聊天或口头沟通。系统只收集候选证据，必须由 PM 点击“确认复核通过”。

同一个人兼任组长和 BD 时，通知去重，但复核和 BD 接收仍分别留痕。

项目开工依据可以来自邮件、聊天、订单或口头通知。PM 确认接入后，系统生成可编辑的开工邮件草稿。发送正式开工邮件后，项目进入制作状态并冻结基准排期。

### FR-012 追加需求

追加需求必须与普通反馈分开，形成独立变更单、报价版本、人天和排期影响。

未受影响资产继续制作；受影响资产进入“等待追加报价”并暂停阶段计时。追加报价确认后，由 PM 手工更新相关排期。

### FR-013 结项与出账

进入结项前自动检查：

- 所有资产完成最终阶段并有客户确认。
- 没有未关闭反馈。
- 没有未决追加需求或报价。
- 没有未处理排期节点。
- 最终提交版本和客户确认依据可追溯。

PM 确认结项后，生成通知总监整理最终包的邮件草稿。系统可以从回复邮件或固定目录发现最终包候选路径；PM 核对后生成 IT 剪切备份通知。

IT 回复邮件是备份完成的正式信号。PM 确认后，系统按照固定结算模板汇总原报价、追加报价、最终资产数量、客户确认和备份信息，生成 BD 出账通知。发送后项目归档，PM 流程结束。

### FR-014 Excel 导入与导出

M1 支持从现有排期 Excel 导入项目、资产、阶段、人天和日期。导入流程必须先预览、验证、显示错误，再由用户确认落库。

导出至少包含项目总览、资产阶段排期、风险、修订记录和人天。

Excel 不再与工作台双向同步；导入完成后，工作台是唯一正式数据源。

### FR-015 LLM 供应商预设

首版设置页预设：OpenAI、Azure OpenAI、Anthropic、Google Gemini、DeepSeek、阿里云百炼/通义千问，以及自定义 OpenAI 兼容接口。

供应商预设包含接口地址、鉴权方式和默认参数；用户只需填写 API Key，再测试连接并选择可用模型。模型列表优先从供应商接口获取，不能获取时使用可编辑的模型名。

API Key 使用 Windows DPAPI 加密，不写入数据库明文字段、普通配置、日志或导出文件。

## 10. 状态模型

### 10.1 项目状态

`报价中 → 待开工确认 → 制作中 → 结项中 → 可通知出账 → 已归档`

已归档项目可以由 PM 重新打开；必须记录原因和时间。

### 10.2 资产阶段状态

`未开始 → 制作及内部审核中 → 团队已交接 → 待提交客户 → 等待客户确认 → 客户通过`

分支状态：

- 客户反馈逾期。
- 返修中。
- 等待追加报价。
- 排期待确认。
- 已延期。

### 10.3 反馈状态

`待确认 → 已确认 → 修改中 → 待重新提交 → 已重新提交 → 客户关闭`

### 10.4 结项状态

`结项检查 → 等待最终包 → 最终包待确认 → 等待 IT 备份 → 备份待确认 → 待通知 BD → 已归档`

## 11. 排期与风险规则

### 11.1 日期类型

- 基准日期：冻结，只能查看。
- 当前日期：由 PM 手工修改。
- 实际日期：由已确认事件或 PM 操作写入。

### 11.2 工作日日历

- 默认周一至周五为工作日。
- 公司节假日不计入人天。
- 特殊工作日和加班日可按日历配置。
- T-1 指计划完成日前一个有效工作日。

### 11.3 延期归因

必须选择以下一种：

- 团队制作延期。
- 客户反馈延迟。
- 客户返修轮次增加。
- 需求变更或追加需求。
- 外部依赖。
- PM 手工调整。
- 其他；必须填写说明。

### 11.4 手工重排

系统只计算和展示潜在影响，不自动改变后续日期。当前阶段延期后，后续阶段进入“排期待确认”，由 PM 逐项或批量修改。

## 12. AI 与自动化边界

### 12.1 AI 可以做

- 分类消息类型。
- 提取项目、资产、阶段、日期、路径和人员。
- 合并连续反馈并生成摘要。
- 建议风险、收件人和下一步动作。
- 生成邮件或群消息草稿。
- 识别截图中的文字和反馈点。

### 12.2 AI 不可以直接做

- 发送邮件或群消息。
- 修改正式项目状态。
- 调整排期。
- 移动、删除或覆盖资产文件。
- 确认报价、开工、结项或出账。

### 12.3 安全控制

- 公司已允许真实业务内容发送到获批的大模型 API。
- 仍支持按项目禁用云端 AI。
- 附件仅在当前任务需要时发送。
- API Key、邮箱凭证和本地文件凭证永不进入提示词。
- 保存模型、请求类型、输入范围摘要和结果，不记录密钥。

## 13. 非功能需求

### NFR-001 平台

- Windows 11 x64；Windows 10 仅限公司仍处于 ESU/LTSC 支持周期内的设备。
- 经典版 Outlook 为 M2 邮件接入前提。
- 应用采用自包含 x64 发布，试用电脑无需单独安装 .NET Runtime。

### NFR-002 性能

- 冷启动至首页可交互不超过 5 秒，目标设备为近五年企业办公电脑。
- 10 万条候选消息下，常用筛选在 500 毫秒内返回。
- 导入 5,000 条资产阶段记录时，预览在 10 秒内完成。
- 连接器后台处理不得阻塞 UI 线程。

### NFR-003 可靠性

- 所有正式状态变更使用数据库事务。
- 强制退出后不产生半完成状态。
- 每次启动执行数据库完整性检查和待恢复操作检查。
- 本地自动备份采用轮换策略，恢复前先验证备份完整性。

### NFR-004 安全

- 数据目录仅当前 Windows 用户可读写。
- API Key 和数据库密钥使用 DPAPI 保护。
- 数据库采用加密 SQLite 提供程序；发布前必须通过“文件离线不可读”测试。
- 日志不记录正文、附件内容、密钥和完整路径凭证。
- GitHub 仓库不得包含真实客户、项目、邮箱和文件盘信息。

### NFR-005 可测试性

- 领域层不依赖 WPF、Outlook、文件系统、系统时钟或真实数据库。
- 工作日、风险、状态机和排期修订全部使用单元测试覆盖。
- Outlook、文件和 AI 通过接口适配，测试使用替身。
- 每个里程碑提供至少一个端到端验收场景。

### NFR-006 可观察性

- 记录连接器状态、同步时间、失败类型和重试次数。
- 操作审计记录用户确认、状态变化、排期修订和草稿创建。
- 日志支持一键导出脱敏诊断包。

## 14. 技术与运营约束

- 工作区当前尚未初始化 Git 仓库。
- 首版仅支持单用户，不实现共享数据库、登录、权限角色或实时协作。
- 企微和飞书接入必须先通过公司管理员审批与接口可行性验证。
- Outlook 经典桌面对象模型接入必须隔离在基础设施层，并在独立 STA 线程执行。
- `SQLitePCLRaw.bundle_e_sqlcipher` 2.1.11 已停止维护。项目负责人已接受在 M1 使用该依赖，并负责后续内部维护或替换；每次发布前必须执行加密、恢复和升级兼容性验证，并记录替换策略。
- 公开 GitHub 发布前必须完成许可证选择和所有样例脱敏。

## 16. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 企微/飞书权限未获批 | 项目群无法全自动采集 | 官方接口验证前置；保留转发、粘贴和截图导入 |
| Outlook 对象模型不稳定或客户端未运行 | 邮件同步中断 | 连接状态可见、可重试、游标幂等、手动刷新 |
| AI 误分类 | 错误项目或任务 | AI 仅候选；高风险低置信度必须人工确认 |
| 排期数据维护量过大 | 用户重新回到 Excel | 批量编辑、模板、拖动调整、键盘操作和 Excel 初次导入 |
| 本机故障 | 单用户数据丢失 | 自动轮换备份、恢复演练、加密迁移包 |
| 数据库加密依赖维护风险 | 安全或升级阻塞 | 固定版本、加密测试、发布前安全评审、记录替换路径 |
| 首次范围过大 | 长期无法形成可用版本 | M1–M5 独立交付；先完成可用排期控制塔 |

## 18. 术语

- **候选卡片**：由连接器或 AI 生成、尚未改变正式业务状态的信息记录。
- **项目控制塔**：项目、排期、风险和操作历史的正式数据中心。
- **基准排期**：开工时冻结的原始承诺日期。
- **当前排期**：PM 根据实际情况手工维护的最新预测日期。
- **T-1**：计划完成日前一个有效工作日。
- **反馈批次**：客户在同一次提交后给出的整体反馈集合。
- **排期待确认**：某个变化可能影响后续节点，但 PM 尚未完成手工重排。
