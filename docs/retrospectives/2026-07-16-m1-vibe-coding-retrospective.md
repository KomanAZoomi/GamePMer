## 2. 失败判定（用户原话要点）

1. 方向错误——做 exe 可以，但做网页也可以，形态不是核心问题。
2. **前端设计太差**。
3. **录入排期和档期太过简单**。
4. **无法看到排期节点**。
5. **甘特图不能正常反映**。
6. **demo 完成前没有预设示例项目数据用于展示**。
7. 最不能理解的：经过 superpowers 和各种需求对齐，做出来的东西仍然大相径庭。

## 3. 根因分析（按影响排序）

### 根因一：文字对齐代替了体验对齐

所有对齐产物（PRD、设计文档、实施计划）都是纯文字，**全程没有一张界面图、没有一个原型**。用户签字认可的是"系统应支持资产阶段级排期录入"这类句子——同一句话既可以实现成用户想要的东西，也可以实现成塞满 `yyyy-MM-dd` 文本框的程序员表格。文字无法传递界面预期。

> 教训：**文档越厚，对齐越假。UI 类产品的对齐必须用图，不能用字。**

### 根因二：验收标准错位

全程的"绿灯"是工程绿灯：测试通过、加密数据库离线不可读、备份可恢复、CI 通过。用户的真实验收标准是：录排期顺不顺手、节点看不看得见、甘特图能不能用。测试验证了正确性，没有验证价值——**绿的是错的东西**。

### 根因三：实现顺序倒置

大量精力花在用户永远看不见的地方（SQLCipher、DPAPI、AES-GCM 迁移包、备份保留策略），而用户每天要摸的排期录入和甘特图是最后拼进一个窗口的"简化版"（按钮代替拖拽）。对个人生产力工具，**体验就是产品本身**，基建应该在体验验收通过之后做。

### 根因四：跳过了原型阶段

用 PBR 管线类比：没做中模就直接进了贴图。用户第一次看到界面就是最终界面，没有任何中途修正的机会。

### 根因五：没有示例数据

首次打开应用是空表格、空甘特。评估一个排期工具却没有排期可看。README 的发布检查清单里写了"使用模拟项目编写示例"，但从未进入应用本身。

### 根因六：交付批量太大

用户授权"继续直到完成"后，六大功能块一口气做完才交付。正确做法是**即使被授权连续推进，也必须在每个可视化节点主动停下给用户看截图**。这一条是执行责任。

### 根因七：技术栈放大了所有问题

WPF 手写 XAML、无设计器预览、反馈靠截图。exe 本身不是错，错在界面风险最高的项目里选了界面迭代最慢的技术，并且把原型和产品合并成了一步。

### 最讽刺的对照

这个产品自己的核心领域规则是：**"每个阶段必须经过客户确认才能进入下一阶段"**（中模不过审不许做高模）。但开发它的过程完全没有遵守这条规则——我们给产品设计了阶段验收门，却没给开发过程设计。

## 4. 做对了什么（可保留的资产）

以下内容质量合格，若项目重启可直接复用（全部在 `feat/m1-foundation` 分支）：

- **领域模型**：工作日日历（节假日/加班日覆盖、T-1、按工作日移动）、2D/3D 阶段模板、基准/当前/实际三套日期、基准冻结不可覆盖、客户确认门、排期修订归因（PRD 11.3 七种原因）、风险引擎（T-1/到期/团队延期/客户反馈逾期/待重排）。
- **Excel 导入导出**：预览校验精确到行列、模板完整性检查、round-trip 测试。
- **加密与备份**：DPAPI 密钥、SQLCipher 库、在线备份+完整性验证、14天+4周保留、AES-GCM 迁移包。
- **测试资产**：74 个测试含一条端到端验收场景（导入→冻结→修订→风险→导出→备份→恢复）。
- **文档**：PRD 的领域知识部分（状态模型、延期归因、责任边界）依然准确。

失败的是**呈现层和流程**，不是领域理解。

## 5. Vibe Coding 阶段门流程（对标 PBR 管线）

每个阶段产出**用户看得见的东西**，用户验收通过才进入下一阶段。未经用户过目的阶段成果视为未完成。

| 阶段 | PBR 类比 | 产出 | 验收标准（用户来验） |
| --- | --- | --- | --- |
| **S0 需求钉子** | 原画/参考 | 一页纸：核心用户场景 + **5 分钟演示脚本**（例："导入这份 Excel → 看到 3 个项目的甘特 → 拖动一个节点 → 出现风险提示"） | 用户 5 分钟读完，说"对，就是这个" |
| **S1 界面原型** | 中模 | 每个主界面的静态稿（HTML/图片均可），**自带真实感示例数据**，零业务逻辑 | 用户逐屏确认布局、字段、信息密度、术语 |
| **S2 可交互切片** | 高模 | 核心操作真实可点（录排期、看节点、拖甘特），数据允许是假的/内存的 | 用户亲手操作 10 分钟，模拟一天的真实工作 |
| **S3 数据做实** | 低模/拓扑 | 真实领域规则、校验、持久化；自动化测试在这个阶段写 | 用户的真实 Excel 导入后显示正确 |
| **S4 加固** | 烘焙 | 加密、备份、异常处理、性能 | 工程检查清单（测试绿灯此时才作为验收标准） |
| **S5 打磨发布** | 贴图/LOD | 空状态、示例数据模式、安装包、使用文档 | 在干净机器上按 S0 演示脚本完整走一遍 |

## 6. 硬规则清单

1. **不见原型不写业务代码**——S1 没过，S2 不开工。
2. **每阶段结束必须真人过目**。即使用户说"继续到完成"，也在每个可视化节点停下给截图/演示。
3. **示例数据是一等公民**：从第一张原型图开始，任何界面不允许空着展示。
4. **对齐文档限两页**，UI 用图不用字。超过两页的文档等于没对齐。
5. **演示脚本驱动开发**：S0 定义的 5 分钟演示，从 S2 起每个阶段都必须保持可运行。
6. **原型期选最快的介质**：哪怕最终目标是 exe，界面验证也可以先用网页做——先验对，再验形态。
7. **基建排在体验之后**：加密/备份/打包等不可见工程，在体验（S2）验收通过前不投入。

## 7. 新项目启动检查单（开工前逐项确认）

- [ ] 有一页纸需求钉子，用户 5 分钟读完并认可
- [ ] 5 分钟演示脚本已写好，双方认可
- [ ] 主界面原型（带示例数据）已画出并经用户逐屏确认
- [ ] 已明确"哪些是用户每天摸的交互"（优先做）和"哪些是不可见基建"（最后做）
- [ ] 已约定阶段验收节奏：谁看、看什么、多久看一次
- [ ] 技术选型以迭代速度为第一标准，形态（exe/网页）第二

## 8. 一句话总结

这次不是代码失败，是流程失败：**我们用造引擎的严谨造了一台没人想开的车。** 测试、架构、加密都对，但它们排在了"用户能不能舒服地看排期"后面本该排的位置。下次，从一张带假数据的界面图开始。
